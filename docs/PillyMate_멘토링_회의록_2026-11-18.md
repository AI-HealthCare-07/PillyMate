## 2. 전체 개발 방향 및 핵심 원칙

### 2.1 문제 정의 → 문제 해결

- 서비스를 **왜 만드는지**, **누가 사용하는지**, **어떤 문제를 해결하는지** 먼저 명확히 해야 함.
- 페르소나 1을 기준으로 가장 중요한 사용자 흐름과 **핵심 가치(Core Value)** 를 정의해야 함.
- 앱을 시연할 때도 “어떤 문제를 해결하기 위해 만들었는가”가 분명히 드러나야 함.
- 문제를 정의한 뒤 안전성·속도 등 여러 관점에서 해결 방안을 검토할 것.

### 2.2 PRD·요구사항 정의서·설계의 역할

- 문제와 대상 사용자, 제품 목적을 설명하는 앞부분의 문서는 **PRD(Product Requirements Document)** 관점에서 이해할 수 있다고 설명.
- 요구사항 정의서와 PRD 성격의 내용을 구분해 정리하는 방향에 긍정적 의견.
- 요구사항 정의서에는 처음에 “있으면 좋겠다”는 기능을 폭넓게 기록하되, 실제 구현 우선순위를 조정해야 함.
- 요구사항 정의 → 구현 방식 설계(ERD 등) → 프로토타입·구현 결과 검토 → 요구사항 보완의 짧은 반복을 권장.
- 프로토타입을 보며 요구사항 정의서를 계속 고치는 **애자일 방식**을 강조.
- 요구사항 정의에 충분한 시간을 들이는 것은 적절하지만, 문서 완성만을 기다리며 구현을 미루지 말 것.
- 기본 문서 폼과 포함할 항목에 관한 정보도 공유할 예정이라고 언급. 양식 자체보다 내용이 중요하다는 취지.

### 2.3 6주를 두 번의 사이클로 운영

- 6주 전체를 한 번의 개발 사이클에 쓰지 말 것.
- 1차 사이클에서는 기능을 과감히 줄여 **2주 차까지 동작하는 MVP**를 만드는 방향을 제안.
- 예시로 전체 기능이 100개라면 처음에는 약 30개만 구현해보고, 나머지 70개 중 불필요한 기능을 제거하거나 다음 사이클로 넘기는 방식 제시.
- 2차 사이클에서 사용자 흐름과 구현 결과를 바탕으로 추가·수정하고 6주 차에 마무리.
- 동일한 입력에 대해 복약 가이드와 챗봇 응답이 일관되게 나오도록 하는 초기 구현도 제안.
- 참고 자료: [Making Sense of MVP](https://blog.crisp.se/2016/01/25/henrikkniberg/making-sense-of-mvp)

## 3. 질의응답 및 기능별 멘토 의견

### 질문 1. 페르소나 및 1차 MVP 범위

- 페르소나 6개는 1차 개발 범위로 많다는 의견.
- **페르소나 1을 중심으로 1차 사이클**을 빠르게 완성하고 이후 확대 여부를 판단할 것을 권장.
- 회의 메모에는 페르소나 **3·4·5번에 취소선을 표시해 2차 사이클로 미루자**는 제안이 기록됨.
- **추가 확인:** 페르소나 2·6의 처리 방침은 이 메모만으로 명확하지 않음.

### 질문 2. 만 14세 미만 자녀의 동의

- 구현 자체는 가능하며 초기에는 최소한의 동의 흐름을 고려할 수 있다는 취지.
- 구체적인 동의 방식과 법적 적합성은 별도 법률 검토가 필요함.
- 1차 MVP에서 과도하게 복잡한 동의 체계를 만들 필요는 없다는 조언.
- **주의:** 이 의견을 법적 요건이 충족되었다는 확인으로 해석하면 안 됨.

### 질문 3. 의약외품·처방약 중복 확인

- 포괄적인 중복 판단은 쉽지 않으므로 **제한된 몇 가지 사례**를 목표로 삼는 방안 제안.
- 전체 범위로 확대하는 작업은 시간과 인력이 남을 경우 검토.

### 질문 4. 생활습관 가이드

- 실제 보호자 등 주변 사용자에게 물어보고 필요한 안내 범위와 내용을 다시 정해보라고 제안.
- 기능 자체보다 사용자가 어떤 내용을 실제로 필요로 하는지 확인할 것.

### 질문 5. 바로 진료받아야 할 신호 및 챗봇 안전

- 의료 안전을 비기능 요구사항에서 중요하게 다뤄야 함.
- 극단적이거나 위험한 질문·상황에 대비한 안전장치가 필요함.
- 예시: 보호자가 아이 돌봄 중 자해 의사를 표현하는 경우, 약을 더 빨리 먹이거나 과량 복용시키려는 취지의 질문을 하는 경우.
- 위험 시나리오를 미리 나열하고, 챗봇의 응답 제한 및 도움 요청 안내를 설계할 필요가 있음.
- **추가 확인:** 구체적인 위험도 분류와 응답 정책은 팀에서 별도 설계·검토해야 함.

### 질문 6. PWA 웹푸시

- 웹푸시는 구현 환경과 플랫폼별 제약 때문에 까다로울 수 있음.
- **1차 버전에서는 실제 웹푸시 대신**, 홈 화면에 알림 목록·알림 메시지 영역을 두어 “언제 어떤 알림을 받았는지” 보여주는 방식 제안.
- 실제 푸시 발송 기능은 이후 사이클에서 검토 가능.

### 질문 7. 투약의뢰서 및 기술 난이도

- 투약의뢰서의 서명·다운로드 기능 자체는 상대적으로 난도가 높지 않다는 의견.
- AI를 사용하지 않는 일반적인 가이드 기능도 상대적으로 구현 난도가 낮다고 평가.
- 반면 **LLM·OCR·RAG**가 주요 기술적 난관이며, 처방전을 올린 뒤 해당 정보를 근거로 챗봇이 답하는 과정은 시행착오가 발생하기 쉬운 부분이라고 설명.
- 알약 사진을 촬영해 약을 식별하는 기능은 약 2~3주가 소요될 수 있다는 추정과 함께, 시간이 남으면 시도하는 후순위 기능으로 제안.
- **참고:** 멘토님의 기간·난도 평가는 경험 기반 추정으로, 실제 개발 일정이 보장된 것은 아님.

### 질문 8. 프로젝트 평가 가능성 및 소아 검증

- 컨셉은 데이터 접근의 어려움과 분야 특수성 때문에 좋은 평가 가능성이 있다는 긍정적 의견.
- 다만 **소아 연령별로 LLM 안내의 적절성을 어떻게 검증할 것인가**라는 문제를 특히 제기.
- 이 문제를 해결한다면 평가상 강점이 될 수 있다고 언급.
- 회의 중 “8점”이라는 표현이 있었으나, **실제 평가 점수나 보장으로 해석하지 않음**.

### 질문 9. 데이터 확보·합성 데이터

- 실제 처방전 데이터 확보는 어려울 수 있으며, IRB 등 절차를 진행하기에는 6주가 짧을 수 있다는 의견.
- 개발·시연 목적이라면 Claude 등 생성형 AI로 **가상의 처방전**을 생성하고 질병코드를 섞는 방법을 제안.
- 데이터를 구하는 일에 과도한 시간을 쓰기보다 부모에게 제공할 **가이드 생성 결과물의 품질**에 집중하라는 취지.
- 프로젝트 기간 안에서 별도의 LLM 모델 학습은 현실적으로 어렵다는 취지의 언급.
- **주의:** 합성 처방전은 실제 의료 데이터나 의학적 검증을 대체하지 않으며, 질병코드·약품명·복용 지시의 유효성을 별도로 검토해야 함.

## 4. 비기능 요구사항(NFR) 검토

- 오즈코딩스쿨에서 요구하는 성능 기준이 현재 비기능 요구사항에 반영되어 있는지 확인할 것.
- 의료 안전·보안 관련 요구사항 중 빠진 항목이 없는지 검토할 것.
- 비기능 요구사항은 문서에만 두지 말고, 개발 중간마다 구현 방향을 확인하는 **검증 도구**로 활용할 것.
- 기능을 추가하거나 제외할 때도 비기능 요구사항과의 정합성을 확인할 것.
- 특히 소아 안내의 안전성, 일관된 답변, 위험 질문 대응 등을 구체적인 검증 항목으로 발전시킬 필요가 있음.

## 5. ERD·API 명세서에 관한 의견

### ERD

- 우선 1차 ERD를 작성하고, 테이블별로 나누어 원하는 기능을 실제로 표현하는지 검토할 것.
- 컬럼의 **단위와 자료형**을 확인할 것.
- 예를 들어 수치 계산이 필요하지 않은 값을 텍스트로 저장했다면, 그 이유가 요구사항에 부합하는지 설명할 수 있어야 함.
- ERD의 형태보다 **데이터 구조가 구현 목적을 충족하는지**가 중요함.

### API 명세서

- 오즈코딩스쿨에서 제공한 템플릿을 사용하고 **1차 MVP 범위**에 맞춰 작성할 것.
- 개발하면서 문서가 계속 바뀌므로, 현재 상태를 정리하는 용도로 활용할 것.
- 3주 차 즈음 구현 결과에 맞춰 명세서를 업데이트·최신화하라는 제안.
- 개발이 계속되는 동안 문서가 완전히 고정되지는 않는다는 점을 고려할 것.

## 6. 멘토님이 제안한 핵심 시연 흐름

**로그인 → 처방전 업로드 → 복약 가이드 제공 → 알림 등록**

- 1차 MVP에서 위 사용자 흐름이 실제로 동작하도록 하는 것이 중요하다고 강조.
- 로그인 화면 자체보다 처방전에서 가이드로 이어지는 핵심 가치가 드러나야 함.
- 알림은 1차에서 홈 화면의 알림 목록 형태로 단순화하는 방안이 제시됨.
- OCR·LLM·RAG의 통합 동작 여부를 조기에 검증할 필요가 있음.

## 7. 논의 결과 구분

### 멘토 권고·제안(팀 최종 확정 전)

1. 페르소나 1 중심으로 1차 MVP 구성.
2. 2주 차까지 최소 동작 제품을 공격적으로 구현.
3. 6주를 두 개발 사이클로 분리.
4. 1차에서는 웹푸시 대신 앱 내 알림 목록 고려.
5. 알약 사진 인식 및 광범위한 중복 판단은 후순위 검토.
6. LLM·OCR·RAG를 핵심 기술 위험으로 관리.
7. 비기능 요구사항을 지속적인 검증 기준으로 활용.
8. ERD와 API 명세서를 구현 결과에 맞춰 갱신.

- 페르소나 2·6 및 3·4·5의 최종 우선순위.

- OCR 인식 오류 처리와 처방약 식별 실패 시 사용자 흐름.
- 가이드 생성 시 근거 데이터·안전성·연령별 검증 방식.
- 챗봇이 답할 수 있는 질문의 범위와 위험 상황 대응.

- ERD 수정 사항과 담당자 배분.
- 멘토링 일정 최종 확정.
