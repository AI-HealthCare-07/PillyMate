# PillyMate 1차 MVP 개발 방향 및 역할 분담 회의록

- **회의일:** 2026년 11월 19일
- **회의 구분:** 코치님 피드백 및 1차 개발 방향 논의
- **프로젝트:** PillyMate – 진료·처방 정보 기반 복약 안내 및 생활 습관 가이드 생성 서비스
- **기록 기준:** 회의 메모 재구성. 명시적으로 확정되지 않은 사항은 별도 표시

## 1. 회의 목적

1차 개발 사이클의 핵심 기능을 선정하고, DB·API 설계 방향, 담당 업무, 개발 우선순위를 정리한다. 팀원들이 각자 맡은 역할을 학습하고 기능 간 연동을 고려해 개발할 수 있도록 한다.

## 2. 1차 MVP 개발 범위

| 기능 | 논의된 방향 | 비고 |
| --- | --- | --- |
| 로그인·회원가입 | 기본 인증 기능 구현 | 회원관리·권한 관리 |
| 처방전·약봉투 업로드 | 기본 이미지 업로드 기능 구현 | 이미지 저장 및 관리 |
| OCR | 업로드 이미지에서 처방 정보 추출 | 반복 실험으로 정확도 개선 |
| AI 가이드 | LLM을 이용한 기본 가이드 생성 | Structured Output 적용 |
| 푸시 알림 | 1차 기능 후보로 언급 | 실제 구현 범위 추가 협의 |
| 챗봇 | 화면만 구현 | 챗봇 기능은 1차에서 제외 |

**1차 핵심 흐름:** 로그인 → 처방전 업로드 → OCR → 가이드 생성.

초기에는 완전한 부가 기능보다 **기본적인 등록·생성 기능을 먼저 구현**한다.

## 3. 데이터베이스 및 API 설계

### 3.1 DB 우선 구축

- 기존 ERD와 테이블 명세를 바탕으로 DB를 먼저 생성한다.
- 개발 중 DB 구조 변경이 발생하면 **마이그레이션**으로 변경 이력을 관리한다.

### 3.2 API 명세

- 기능을 기준으로 ERD 초안과 API 명세를 정리한 뒤 백엔드 업무를 구분한다.
- 엔드포인트 작성뿐 아니라 **요청 데이터, 처리 과정, 응답 데이터**를 이해하는 것이 중요하다.
- FE·BE·AI 간 데이터 형식을 먼저 합의한다.

## 4. 백엔드 역할 분담

### BE-1: AWS·배포 및 회원관리

- AWS 클라우드 환경 구축 및 배포 관리
- 로그인, 회원가입, 인증·권한 관리
- `boto3` 기반 AWS 리소스 관리 코드 작성
- 다른 백엔드 기능에서 사용할 AWS 관련 모듈 제공

### BE-2: 그 외 API

- 처방전·약봉투 등록 API
- OCR 모듈 호출 및 결과 처리
- 보호자가 수정·확정한 처방 데이터 저장
- 가이드 생성 API 및 관련 DB 조회
- AI 모듈과 API 연동

## 5. OCR 개발 방향

- Clova OCR API의 **템플릿 기능**을 확인하고 활용 가능성을 검토한다.
- 병원별로 처방전·약봉투 양식이 달라질 수 있으므로 여러 형태를 고려한다.
- OCR은 예상보다 까다로울 수 있어, 추출 결과를 비교하며 반복 실험하고 개선한다.
- 추출 결과를 합의된 처방 JSON 형태로 정리해 다음 단계로 전달한다.

## 6. RAG 및 LLM 개발 방향

### 6.1 RAG

- RAG를 담당할 인원을 정해야 한다는 의견이 있었다.
- 백엔드에서 호출할 수 있는 별도 모듈로 구성하는 방향을 검토한다.
- **담당자 및 1차 필수 구현 여부는 추가 협의가 필요하다.**

### 6.2 LLM 가이드 생성

1. DB에서 처방전 데이터, 병명, 특이사항 등 필요한 정보를 조회한다.
2. 조회한 정보로 LLM에 전달할 **Context**를 구성한다.
3. LLM API를 호출하여 기본 가이드를 생성한다.
4. 가이드는 **Structured Output(정형화된 출력)**으로 반환한다.
5. 생성 결과를 저장하고 화면에 전달한다.

처음에는 LLM을 이용한 기본 가이드 생성부터 구현하고, 이후 품질을 개선한다.

## 7. 백엔드와 AI 모듈의 연결 구조

- OCR·RAG 등은 백엔드 내 **별도 모듈**로 분리한다.
- API 코드에서 필요한 모듈을 import하거나 인스턴스를 통해 호출하는 방식을 검토한다.
- 구체적인 호출 구조는 실제 프로젝트 구성에 맞게 결정한다.

```text
프론트엔드
   ↓ 요청
백엔드 API
   ├─ OCR 모듈 호출 → 처방 정보 추출
   ├─ RAG 모듈 호출 → 필요 시 관련 정보 검색
   └─ LLM 모듈 호출 → 구조화된 가이드 생성
   ↓
DB 저장 및 프론트엔드 응답
```

> 위 구조는 회의 내용을 이해하기 위한 개념도이며, RAG의 1차 적용 여부는 확정되지 않았다.

## 8. 개발 우선순위 및 작업 흐름

| 단계 | 우선 작업 | 주요 담당 |
| --- | --- | --- |
| 1 | ERD·테이블 명세 확인 및 DB 구축 | BE |
| 2 | API 명세와 공통 JSON 형식 합의 | BE·FE·AI |
| 3 | 로그인·회원가입 기능 구현 | BE-1·FE-1 |
| 4 | 처방전·약봉투 업로드 구현 | BE-2·FE-2 |
| 5 | OCR 추출 및 결과 확인·수정 구현 | AI-1·BE-2·FE-2 |
| 6 | LLM 가이드 생성 및 화면 출력 | AI-2·BE-2·FE-1 |
| 7 | 전체 흐름 통합 테스트 | 전원 |

**진행 원칙:** 작업 간 선행 조건은 지키되, 공통 명세가 확정되면 역할별 구현은 병렬로 진행한다.

## 핵심 요약

이번 회의에서는 **DB를 먼저 구축하고, API 명세를 기반으로 역할을 나눠, 로그인 → 업로드 → OCR → 가이드 생성의 기본 흐름을 1차 MVP에서 구현**하는 방향을 논의했다. OCR은 반복 실험으로 개선하고, LLM 가이드는 DB 조회 데이터로 Context를 구성해 Structured Output으로 생성한다. 챗봇은 화면만 만들며, 푸시 알림과 RAG의 구체적인 1차 범위는 추가 협의한다.
