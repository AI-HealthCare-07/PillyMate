# PillyMate 멘토링 회의록

-   **일자:** 2026.11.24 (화)
-   **참석:** 멘토님 및 4조 팀원
-   **핵심 목표:** 11/26(목)까지 공통 코드 통합 및 실제 API 연동 확인

## 1. 팀 협업 및 코드 통합 (최우선)

-   새로운 기능을 추가하기보다 지금까지 개발한 코드를 먼저 통합할 것.
-   팀장 주도로 목요일까지 공통 버전을 만들고, DB 구성 및 실제 API 호출까지 확인할 것.
-   프론트엔드끼리, 백엔드끼리, 그리고 서로 연관된 기능 담당자 간 소통을 강화할 것.
-   중간중간 개발 진행 상황과 코드 충돌 여부를 확인한 후 개발을 이어갈 것.

## 2. 프론트엔드 및 디자인

-   현재 디자인에서 AI로 생성한 느낌이 많이 나므로 색상, 레이아웃, 화면 구성을 개선할 것.
-   모바일 중심으로 설계하고, 데스크톱과 모바일의 화면 구성에 차이를 둘 것.
-   디자인은 지속적으로 고민하고 개선할 것. 멘토님도 관련 스킬을 찾아 공유해 주실 예정.
-   참고: [Claude Code Frontend Design 플러그인](https://claude.com/ko/marketplace/plugins/frontend-design)

## 3. OCR 및 복약 알림

-   인식률 저하 문제를 개선하기 위해 General OCR을 활용할 것.
-   혜진님이 진행한 신뢰도 관련 작업을 활용하고, 일반 필드와 테이블 필드의 `inferConfidence` 값을 확인할 것.
-   OCR 신뢰도에 따라 사용자에게 재촬영 또는 직접 수정을 안내하는 UX/UI를 구성할 것.

  신뢰도 (논의 기준)     처리 방향
  ---------------------- --------------------------------
  80% 이상               인식 결과 확인
  60% 이상 \~ 80% 미만   신뢰도가 낮은 항목 직접 수정
  60% 미만               사진 재촬영 또는 재업로드 안내

-   재촬영 안내를 먼저 구현하고, 이후 특정 항목 수정 및 상세 안내 기능을 추가할 것.
-   촬영 가이드라인은 구현 난이도를 고려하여 후순위로 검토.
-   하루 복용 횟수 등 필수 정보가 추출되지 않으면 자동 알림에서 제외한다는 기존 명세가 실제 코드에 반영되어 있는지 확인할 것.
-   참고: [NAVER Cloud General OCR 공식 문서](https://api.ncloud-docs.com/docs/ai-application-service-ocr-ocr)

※ 신뢰도 기준과 적용 단위는 실제 테스트 후 확정 필요.

## 4. 개인정보 및 이미지 저장

-   OCR 처리에 필요한 이미지 원본과 마스킹 이미지는 영구 저장하지 않고, 처리 완료 후 삭제할 것.
-   추출된 텍스트 중 서비스에 필요한 데이터만 JSON 등으로 구조화하여 DB에 저장할 것.
-   개인정보 및 민감정보의 수집·보관·삭제 범위를 팀 내부에서 논의하고 다음 멘토링에서 재확인할 것.

## 5. 카카오 로그인 및 회원가입

-   카카오 로그인은 최초 회원가입까지 연계할 것.
-   이메일 정보 수집 여부와 필수 회원정보를 결정할 것.
-   일반 이메일 가입을 유지한다면 이메일 점유 인증이 필요함.
-   카카오 로그인 사용 시 별도 회원가입 화면을 간소화하고, 필요한 추가 정보만 입력받는 방향을 검토할 것.
-   중복 가입 및 동일 사용자 식별 방식(CI 등)을 논의할 것. 카카오 로그인만으로 본인확인이 완료되거나 CI가 자동 제공되는 것은 아니므로 제공 조건 확인 필요.

## 6. LLM 복약가이드 및 케어가이드

-   OCR로 추출하고 확인한 복약 정보를 DB에 저장한 후, 정확한 근거 데이터를 LLM에 전달하여 가이드를 생성할 것.
-   원하는 답변에 포함될 항목과 출력 예시를 구체적으로 정의할 것.
-   System Prompt와 User Prompt의 차이를 학습하고 One-shot / Few-shot Prompt 활용을 검토할 것.
-   JSON 형태로 응답을 구조화하고, 복용량이나 복용 횟수 등 처방 정보를 LLM이 임의로 생성하지 않도록 할 것.
-   참고: [프롬프트 엔지니어링 자료](https://wikidocs.net/blog/@datalearners/27073/)

## 7. DB 및 배포 환경

-   현재는 각자의 로컬 DB를 사용하여 개발 및 통합 테스트를 진행할 것.
-   공용 서버 DB는 여러 팀원이 동시에 변경할 수 있으므로 현 단계에서는 지양.
-   EC2, Docker, RDS 등 배포 환경은 실제 배포 단계에서 검토할 것. RDS 없이 구성하는 방법도 있음.
-   참고: [Docker 및 EC2 구성 자료](https://app.notion.com/p/Docker-EC2-320caf5650aa8008a93dc32208722169)
