# 가이드 약 정보(reference) 개선 — 작업 인계 (2026-11-27)

> 새 세션에서 이 문서만 읽고 바로 이어서 작업할 수 있게 정리했어요.
> 가이드 담당과 합의해서 이 작업은 이 문서를 받는 사람(thgPwls98)이 맡기로 했어요.

## 1. 왜 하는가

요구사항: **사용자 진료 기록 및 복약 정보를 기반으로 맞춤형 복약/생활습관 가이드를 자동 생성** (맞춤형 복약·생활 안내, 개인별 건강 상태 반영)

가이드 LLM(Claude Haiku)은 프롬프트 규칙상 **약에 대한 사실(효능·주의·부작용·보관)을 `reference`에서만** 가져와요.
그런데 `reference`를 채우는 검수 데이터가 **21개 약뿐**이라, 그 밖의 약은 전부 "참조 정보 없음"이 되고

- `purpose`가 "어떤 약인지 약사에게 확인해 주세요."가 되고
- `cautions`·`common_side_effects`·`storage`가 비고
- 거의 모든 약에 "약사 확인 필요"가 붙어요.

→ 규칙(안전선)은 그대로 두고, **근거 데이터(reference)를 넓혀서** 가이드 내용을 풍부하게 만드는 게 목표예요.

## 3. 지금 reference가 만들어지는 흐름

```
POST /prescriptions/{id}/guide
 └ app/services/prescriptions.py  create_guide()
    └ guide_inputs()                       ← DB 행 → dict. ⚠ insurance_code를 넘기지 않음
       └ app/services/guide/service.py  generate_guide()
          ├ normalize_medication()         ← ingredient_of(name)로 영문 성분 채움 (app/services/guide/merge.py INGREDIENT_RULES, 손으로 적은 표)
          ├ references_for()
          │  └ app/services/guide/drug_reference.py  build_references()
          │     └ DrugRefIndex.find()  매칭 순서:
          │        1) 보험코드 → drug_refs의 insurance_codes   ⚠ drug_refs에 insurance_codes가 없고, 위에서 코드도 안 넘어옴 → 항상 실패
          │        2) 이름 정확히 일치 (normalize_name 후, key + names)
          │        3) 비슷한 이름 (difflib ≥ 0.88)
          │        4) 같은 성분 (med["ingredient"] 또는 이름 괄호 속 글자) → 요약에 "같은 성분의 다른 제품 정보" 표시
          │        5) 없음 → reference 없음
          │     └ summarize()  → "[출처…] 성분: … 효능: … 주의: … 흔한 부작용: … 보관: …" (약 하나당 600자, MAX_CHARS)
          └ app/services/guide/generator.py  generate() → build_context()의 medications[].reference
             (reference가 없으면 "참조 정보 없음 → 약사 확인 안내")
```

### 1단계: CSV로 성분을 찾아 검수 데이터에 연결하기
검수된 문장만 쓰니 안전성은 그대로예요. 위 측정 결과상 **적중률을 올리는 효과는 없고**,
의미는 **연결이 맞는지 확인하는 것**(손으로 적은 성분 표 대신 허가 데이터의 M코드로 같은 성분인지 판단 → 로코이드 같은 잘못된 연결 막기)이에요.
2단계보다 먼저 할지는 다시 정하기.

1. **보험코드 넘기기**: `app/services/prescriptions.py` `guide_inputs()`의 `meds_d`에 `"insurance_code": m.insurance_code` 추가
   (`Medication` 모델에 `insurance_code`가 있음 — `app/services/drug_efficacy.py`가 `m.insurance_code`를 씀)
2. **drug_refs 21개에 보험코드·M코드 붙이기**: 각 항목의 `item_seq`로 CSV 행을 찾아 `EDI_CODE`(쉼표 구분)와 `MAIN_ITEM_INGR`의 M코드를 얻음.
   json에 직접 채우거나(빌드 스크립트) 로드할 때 계산 — 새 세션에서 결정.
3. **CSV로 약의 성분(M코드) 찾기**: 처방 약 → (보험코드 일치 → 이름 정확히 일치) → CSV 행 → M코드 집합.
   M코드 집합이 검수 문서의 M코드 집합과 **같으면** 그 문서를 "같은 성분" reference로 씀 (기존 4단계와 같은 표시).
   - 복합제는 집합이 정확히 같을 때만. 부분 일치는 쓰지 않기(짐작 금지 원칙).
   - 제형이 달라도 성분 기준 문서는 쓰되, 기존처럼 "제품별 차이는 약사 확인" 문구가 붙음.
4. **코드 위치**: `app/services/guide/` 쪽에 새 모듈(기능이 드러나는 이름, 예: `permit_ingredient_index.py`)로 두거나,
   이미 CSV를 읽는 `app/services/drug_lookup.py`의 `load_records()`/`get_drug_index()`를 재사용할지 검토.
   reference 코드·데이터는 API 서버 이미지에 들어가도록 `app/` 안에 둔다 (`app/Dockerfile`은 `app/`·`ocr/`만 복사함).
5. **테스트**: 매칭 단위 테스트 추가 (보험코드로 찾기, 이름으로 찾기, 복합제 부분 일치는 안 됨, CSV 없으면 기존 동작 그대로).
6. **효과 측정**: `scripts/rag/check_match_rate.py`
   ```bash
   uv run python scripts/rag/check_match_rate.py --medication data/sample/medication_from_ocr.csv
   ```
   지금 54%. (`data/sample/medication.csv`는 drug_refs.json과 같은 약들이라 100%가 나와 의미 없음)

**완료 기준**: 측정용 목록 적중률이 54%에서 떨어지지 않음 · 로코이드처럼 성분이 다른 약이 연결되지 않음 · 테스트·ruff 통과.
적중률을 올리는 건 2단계의 완료 기준으로 옮김 (예전에 "참조 정보 없음"이던 약에 `purpose`·`cautions`가 채워지는지 실제 Haiku로 확인).

      "symptom_notes": "설사 하루 5번, 밥을 잘 안 먹어요"}
for label, child in {"age2": {"birth_date": "2024-09-10", "weight_kg": 12.0, "allergies": []},

"어떤 약인지 약사에게 확인해 주세요." + 약사 확인 true. 포리부틴(트리메부틴)은 검수 문서가 없는 성분이라 1단계로는 안 바뀌고 2단계가 필요해요.

## 7. 보류한 프롬프트 문제 (reference 작업 뒤 `prompts.py`에 반영할 것)

실제 Haiku 결과에서 발견:
1. 11살(학령기)인데 `how_to_give`가 2살과 똑같이 "먹여 주세요" → 학령기·청소년은 "스스로 먹게 하고, 먹었는지 확인해 주세요"처럼 쓰라고 **예시 문장까지** 주기
2. 예시에 없는 제형(건조시럽)에 근거 없는 요령("정해진 양의 물에 완전히 녹여서")을 씀 → 예시에 없는 제형은 기본 요령 쓰지 말고 usage·약봉투 안내만 따르게
3. 11살 `purpose`에 reference의 "생후 3개월 이상의…"를 그대로 옮김 → 아이 나이와 맞지 않는 나이 조건은 빼고 쓰게
4. 먹이면 안 되는 경우(과당 불내성)가 `how_to_give`에도 들어가고 `cautions`와 중복 → `how_to_give`는 먹이는 방법만, 금기는 `cautions`에만

## 8. 이 세션에서 발견한 다른 문제 (참고·백로그, 이번 작업 범위 아님)

- **생활 안내가 화면까지 안 감**: `assemble()`이 만든 `home_care[].items[].personal_note`(아이 맞춤 한 줄)와 섹션 제목,
  `focus_points`의 `title`·`why`·`reason_for_child`, `age_notes`를 `app/services/guide/view.py` `build_life()`가 버리고 문장만 펼침.
  프론트 `frontend/src/state/records.jsx` `guideFromServer()`도 `detail`·`sources`를 읽지 않음. 생활 습관은 최대 8줄(`MAX_LIFE`)이고 돌봄 항목이 맨 뒤라 잘림.
- **나이 필터 빈틈**: `generator.py` 459~461줄에서 공통 위험 신호(`common["warning_signs"]`)에 `usable()`을 안 걸어서
  11살에게도 "생후 3개월 미만 아기가 38℃…", "생후 3~6개월…", "기저귀가 6시간 넘게…"가 나옴.
  `ent.handwash`·`doc.diaper6h` 문장에 기저귀가 섞여 있고 나이 조건 없음. 나이 조건 붙은 템플릿 문장이 적음.
- **템플릿 없는 병(`other`)**: `home_care_candidates`가 빈 목록 (프롬프트는 이번에 0개 처리 문구 추가함).
- **약효 배지 서버 경로 두 벌**: 홈 배지는 GET `/prescriptions/{id}` → `app/services/drug_efficacy.py`(식약처 API 실시간, `MFDS_API_KEY` 필요).
  로컬 `envs/.prod.env`에는 키가 비어 있음(실제 배포 서버 값은 미확인). CSV 기반 `drug_lookup.py`는 확정 API 응답에만 쓰임.
  키가 없으면 프론트 `frontend/src/data/efficacy.js`의 손으로 적은 21개 제품·18개 성분으로만 배지가 나옴.
- **확인 화면 409**: `frontend/src/screens/confirm.jsx` 165~166줄이 확정 API의 409(가이드 만든 처방 수정 거절)를 무시하고 진행해
  거절된 수정값으로 건강기록·복약 일정을 덮어씀. 브라우저 뒤로 가기로 확인 화면에 다시 들어올 수 있음. 리뷰 코멘트 초안 정리해 둠(이슈·후속 PR로 낼 것).
